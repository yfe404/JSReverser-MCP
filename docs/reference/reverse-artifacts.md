# Reverse Artifacts

It is recommended that every reverse engineering task writes to a unified task directory:

`artifacts/tasks/<taskId>/`

Public documentation entry points and local task artifacts are separated:

- Public index: `scripts/cases/README.md`
- Official rules / templates / contracts: `docs/reference/`
- Human usage guides: `docs/guides/`
- Local private task artifacts: `artifacts/tasks/<taskId>/`

Reading priority:

1. First reuse existing full-pipeline data in `artifacts/tasks/<taskId>/`.
2. If none exists, refer to abstract cases in `scripts/cases/*`.
3. If still insufficient, create a new task directory using the parameter methodology template and execute.

## Minimum Required Files

The following files constitute the minimum task artifact; missing any of them will affect continuation:

- `task.json`
- `network.jsonl`
- `scripts.jsonl`
- `runtime-evidence.jsonl`
- `env/entry.js`
- `env/env.js`
- `env/polyfills.js`
- `env/capture.json`
- `report.md`

## Optional Files

The following files are added as needed per task and should not all be generated by default:

- `timeline.jsonl`
- `cookies.json`
- `replay/actions.json`
- `run/`
- Site-specific `env/scripts/`
- `run/exported-runtime.js`
- `run/pure-*.js`
- `run/pure_*.py`
- `run/fixtures.json`

Purpose of these files:

- Review page observation evidence
- Track which request, script, or cookie participates in parameter generation
- Record local rebuild progress
- Allow Codex / Claude / Gemini to continue the same task

Notes:
- Executable scripts and pipeline data are placed together in `artifacts/tasks/`; the directory structure is kept stable for reuse.
- `scripts/cases/*` remains abstract templates only; no directly reusable implementations.
- Task skeleton can be directly reused from: `artifacts/tasks/_TEMPLATE/`.
- Real `artifacts/tasks/<taskId>/` are kept locally by default; perform a redaction review before sharing.

## About Python `execjs` and Other External Hosts

If the goal is to have Python directly call a signature function, it is recommended to produce two types of files:

1. Local rebuild files
- Used for environment patching, debugging, reading proxy env logs, and locating first divergence
- Typical files: `env/env.js`, `env/polyfills.js`, `env/entry.js`

2. Portable runtime files
- Used for direct invocation by external hosts
- Typical files: `run/exported-runtime.js`

Recommended workflow:

1. First get the pipeline working in the Node local rebuild
2. First complete minimal causal unit patches based on proxy env logs and `first divergence`
3. Then distill the minimal dependencies into `run/exported-runtime.js`
4. Finally have Python `execjs`, `quickjs`, or other hosts call the exported functions

Do not do it in reverse by patching the environment directly inside `execjs` -- this makes debugging and locating gaps much more difficult.


## About Pure Algorithm Artifacts

For entry conditions and phase protocol, see: `docs/reference/pure-extraction.md`

When a task has moved from `env rebuild` into the pure algorithm extraction phase, it is recommended to produce the following artifacts under the task-local `run/` directory:

- `run/pure-*.js`: Readable pure algorithm implementation
- Optional `run/pure_*.py`: External language implementation
- `run/fixtures.json` or equivalent fixtures: Fixed input, fixed runtimeContext, fixed output
- Pure runtime acceptance records in `report.md`

It is recommended to include at least the following in `report.md`:

- Pure Algorithm Status
- Portable Runtime Status
- Fixture Result
- Server Acceptance
- Drift Boundary

Notes:

- These pure algorithm files are still task-local artifacts and do not belong to the public repository cases
- `scripts/cases/*` can only describe “how to extract pure algorithms” and must not directly store real pure algorithm implementations for any specific site
